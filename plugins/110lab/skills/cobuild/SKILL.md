# CoBuild 跨应用协作

把同一件事在各应用中的记录接起来，并核实每次交接。根据用户本次目标选用下面的路径，单一业务不必跑完整流程。需要了解工具时先用 `cobuild_overview` 离线导航；调用以当前客户端实际发现的工具和 Schema 为准，包内手册是版本快照。

## 选路径

| 用户要做什么 | 起点与后续 |
| --- | --- |
| 从想法发起项目、组建团队或安排里程碑 | [日常运营](../operations/SKILL.md) 的项目流程；确认项目同步结果，再进入需求平台，不把项目分类当成一条需求 |
| 接手需求、修缺陷、推进 PR 或交付 | [需求研发](../requirement-dev/SKILL.md)；以需求 ID 接手，关联实际仓库和知识库，最后核对交付证据 |
| 写方案、整理资料、上传文件或沉淀使用说明 | [知识库](../knowledge/SKILL.md)；优先维护已有页面，再把真实链接回填到获授权的项目或需求 |
| 登记荣誉、处理招新、公共邮件或官网动态 | [日常运营](../operations/SKILL.md)；保存业务事实、准备预览、执行已有授权及系统要求的本人确认，再查最终结果 |
| 某个服务无法连接或身份不符 | [身份连接](../identity/SKILL.md)；只修复所需域，继续不依赖该域的工作 |

## 跨应用时保持一条线

开始时提炼本次要交付的结果和已有授权。人确定目标、关键取舍、人员安排及业务决定；Agent 查真实记录和代码、准备方案、执行已授权动作、核对回执。用户只要方案就停在方案；已经授权实施则持续推进，不重复制造审批关卡。系统明确要求的本人 OAuth 或可信预览确认仍由本人完成。

在当前任务上下文保留关联关系：工作台项目 UUID、需求记录 ID/编号、仓库和分支、PR 地址与实际提交 SHA、知识库页面/文件 ID与版本、未结束操作的回执 ID。不要求为每个任务另建日志。只用明确链接、同步回执或用户指定建立关联，不按同名猜测，不把不同系统的人员 ID 混用。

- 接手已有需求用 `cobuild_requirement_context`，必要时显式提供 `projectId`、`documentIds`；查看 `consistent`、`gaps`、截断及权限缺口。聚合资料不全时继续用原工具读取，不用旧摘要覆盖正文。
- 一步成功、后一步失败时保留已成功的记录及链接，只恢复失败的步骤。没有跨应用事务，不重新立项、重建文档或重复发通知来“重跑全流程”。
- 准备平台流转、PR交付或发布时，用 `cobuild_delivery_check` 辅助核对门禁；只交付本地结果不强制跑发布检查。`platformReady` 不是 CI、部署或实际验收；还要检查 `snapshotComplete`、PR 完整性和真实提交，缺少证据就保留缺口。
- 结果未知时先查原操作并回读目标，沿用原键和原参数；不换键重复执行。各业务回执和版本字段不可互换，详见 [交接与恢复](references/handoffs.md)。

## 给用户的结果

按本次范围交代已落地的内容和可点击的记录链接、已验证证据、仍在进行或被阻塞的步骤及下一步。分别说清代码、平台回写、PR、部署、发送/发布，不用一个“已完成”代替所有状态。不要声称未发现的工具、未加载的新版插件或尚未授权的服务可用。

批改系统、候选人考核、个人 QQ 邮箱及飞书/GitHub 独立连接不是这套 MCP 的隐含能力。需要它们时使用实际已接入的工具或应用页面，并沿用各自账号和权限。

三个聚合入口的参数见 [工作流工具手册](../../docs/mcp-reference/workflow.md)。包内 mcp/cobuild-tools.json 仅保存各业务域原工具，聚合工具由运行时追加；它不是完整 tools/list，不应据它单独断言聚合入口不存在。
